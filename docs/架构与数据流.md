# 架构与数据流

这篇文档讲清楚两件事：**数据从哪来、经过哪些层、最后变成什么**，以及**每层的代码在哪**。
只想知道怎么用，看 [README](../README.md)；只想知道字段长什么样，看 [schema.md](./schema.md)。

## 各层职责

### 1. 采集层：把外部登录态变成文件或 HTTP 响应

这一层**不产生标准格式**，只负责拿到原始数据。它有三种形态：

| 形态 | 例子 | 优点 | 代价 |
|---|---|---|---|
| 本地导出文件 | `weflow-cli export`、`qce export` | 可复现、可离线重跑 | 要人工触发一次 |
| 在线 API | OneBot HTTP、lark-cli、qce qzone | 数据新鲜 | 依赖进程/令牌存活 |
| 浏览器抓页面 | bsk + tieba/zhihu 脚本 | 能拿到没有 API 的内容 | 依赖浏览器扩展连接 |

统一原则：**采集失败不应该让整个流程崩掉**。每个源都有独立的 try/catch，一个源挂了其他照跑。

### 2. 归一化层：`src/core/extractor.js`

一个平台一个 `extractXxx(opts)`，产出 `{ meta, messages, contacts }`：

| 方法 | 入口 | 说明 |
|---|---|---|
| `extractWechat` | 文件 / 数据库 | 两种解析器：`_parseWechatExportArray`（weflow 数组）和数据库直读 |
| `extractQQ` | 文件 / OneBot | 三种输入：OneBot HTTP、`qce` 导出文件（`_parseQQExportFile`）、老格式 |
| `extractQQZone` | qce / 内置 HTTP / 文件 | 优先 `qce qzone --json`，失败回落内置 HTTP |
| `extractFeishu` | lark-cli / 文件 | 先列会话再逐会话拉消息 |
| `extractTieba` | bsk / 文件 | 帖子楼层或吧内列表 |
| `extractZhihu` | bsk / 文件 | 问题首屏回答 |
| `extractBilibili` | MCP CLI | 历史/收藏/热门/搜索/观看时长 |
| `extractAll` | 上面全部 | 按 config 逐个跑，互不影响 |

**归一化的难点不是字段改名，而是“谁发的”和“什么时候”。**
每个平台的 `isSelf` 判定方式都不同，时间戳单位也不统一（详见 [schema.md](./schema.md) 的“已知坑”）。

### 3. 汇总层：`src/core/merge.js`

| 步骤 | 做什么 | 关键决定 |
|---|---|---|
| `_deduplicate` | 按 `messageId` 去重 | 增量模式重叠窗口靠这个兜底 |
| `_deduplicateContacts` | 合并同一会话 | 键取 `chatId \|\| id \|\| name`——只按 chatId 会把跨平台数据塌成一条 |
| `generateStats` | 总数、按年、按会话、发言人排行 | 供分析层喂给 AI |
| `sampleByYear` | 每年抽样 | 长历史（14 年）不抽样会撑爆上下文 |

### 4. 分析层：两条路

**在线（`src/core/analyzer.js`）**

需要 `DEEPSEEK_API_KEY` 或 `ANTHROPIC_API_KEY`。产出固定五段：

```json
{ "epitaph": "...", "trajectory": [...], "relationships": [...], "keywords": [...], "stats": {...} }
```

没有 Key 时 analyzer 会产出**模拟数据**——这是设计上的“能跑通”降级，不是真实分析，别拿去发布。

**离线（`scripts/render.mjs`）**

手写（或让 AI 在别处写好）一份 `analysis.json`，字段与上面一致，直接渲染。
这条路没有 Key 也能出真东西，代价是人要读统计。

### 5. 渲染与展示

- `src/core/generator.js`：`monument.json`（结构化）+ `monument.html`（自包含单文件）
- `scripts/render.mjs`：离线路径的同款产物
- `valley/`：Express + SQLite + React，存多座碑、评论、漂流瓶

## 磁盘上的数据

```
data/
├── raw/<source>/     原始导出（微信/QQ/空间/飞书…），一律不入库
├── unified/          build-from-data.mjs 的产物 + select-personal.mjs 的筛选结果
├── analysis/         analysis.json（AI 或人工）
└── output/           monument.json / monument.html
```

`data/` 整个目录在 `.gitignore` 里，只有 `data/README.md` 入库。详见 [data/README.md](../data/README.md)。

## 两条完整路径

**A. 在线（一次性，需要 Key 与登录态）**

```bash
node src/index.js generate --auto --qzone-uin <QQ号> --output ./output
```

**B. 离线（可复现，不需要 Key）**

```bash
node scripts/build-from-data.mjs            # data/raw → data/unified/unified-data.json
node scripts/select-personal.mjs --context-min 10   # 只留与本人相关的部分
node scripts/render.mjs data/analysis/analysis.json data/output
```

B 的好处是**每一步的中间产物都留在本地**，能对比、能回滚、能给不同的人看不同粒度。

## 支撑脚本

| 脚本 | 作用 |
|---|---|
| `scripts/build-from-data.mjs` | 扫 `data/raw/` 按来源选解析器汇总；`--live` 顺带取在线源 |
| `scripts/select-personal.mjs` | 从全量语料里筛出“与本人相关”（规则见脚本头部注释） |
| `scripts/render.mjs` | `analysis.json` → `monument.json` / `.html` |
| `scripts/dump-unified.mjs` | 不走 data/ 目录，按 config 在线提取一次 |
| `scripts/health-check.ps1` | 数据源自检（OK / FAIL / SKIP 三态），`-Fix` 拉起服务 |
| `scripts/start-valley.cmd` | 后台启动纪念碑谷 |
| `scripts/lark-cli-user-token.js` | 飞书令牌注入 wrapper（两个令牌文件取较新的一个） |

## 为什么这样分层

1. **采集和解析分离**：数据源随时可能挂（cookie 过期、进程没起），解析逻辑不该跟着改。
2. **归一化只有一个出口**：所有平台最终都是 `Message[]`，分析层不需要知道来源。
3. **两套分析**：有 Key 走 AI，没 Key 走人工——保证“没有 API 也能交付真东西”。
4. **默认焚毁**：`--no-burn` 才保留原始数据，擦除能力的边界见 README。
